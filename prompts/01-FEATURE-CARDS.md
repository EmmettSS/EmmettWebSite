## F-01 — محاسبات تاریخ شمسی

**مسیر:** `/fa/tools/tarikh-shamsi/` · `/en/tools/jalali-date/` · **فاز ۲** · **تلاش: S**

### فرضیه
«هر سایت ایرانی با تاریخ شمسی مشکل دارد. یک ابزار که *ریاضیِ درست* داشته باشد، فوراً کیفیت
امت را اثبات می‌کند و برای کلمهٔ کلیدی پرحجم «تبدیل تاریخ شمسی به میلادی» رتبه می‌گیرد.»

### داستان کاربر
توسعه‌دهنده‌ای می‌خواهد بداند «۱۵ روز کاری بعد از ۱۴۰۴/۰۷/۰۱ چه روزی است، با احتساب تعطیلات».
ابزار را باز می‌کند، جواب می‌گیرد، کدش را کپی می‌کند، و می‌فهمد چه کسی این را ساخته.

### UI
- **سه تب:** تبدیل · محاسبات · تبدیل انبوه
- **تبدیل:** ورودی شمسی ↔ میلادی ↔ قمری، زنده (هر تایپ = هر محاسبه)، نمایش روز هفته به فارسی،
  ارقام فارسی در حالت `fa`، دکمهٔ «امروز»
- **محاسبات:** اختلاف دو تاریخ (روز/هفته/ماه/سال) · افزودن/کاهش n روز · **n روز کاری با احتساب
  تعطیلات رسمی** · «چندشنبهٔ چندم ماه» · فاصله تا نوروز/یلدا
- **تبدیل انبوه:** textarea با یک تاریخ در هر خط → جدول خروجی + **دانلود CSV**
- **کد:** تب «کد» با پیاده‌سازی واقعی در JS/Python/Go + دکمهٔ کپی
- **خروجی اشتراکی:** «لینک این نتیجه» → URL با پارامتر (`?d=1404-07-01&to=gregorian`)

### API
```
GET  /api/v1/tools/jalali/convert/?from=jalali&to=gregorian&value=1404-07-01
GET  /api/v1/tools/jalali/diff/?a=1404-07-01&b=1404-08-15
GET  /api/v1/tools/jalali/workdays/?from=1404-07-01&add=15&holidays=1404
GET  /api/v1/tools/jalali/holidays/?year=1404        → نسخه‌دار، قابل کش
```
**منطق اصلی سمت سرور است** (تا SEO Static Bridge خروجی واقعی داشته باشد و کد قابل راستی‌آزمایی باشد)،
با **کش سمت کلاینت** برای حالت زندهٔ تایپ.

### cPanel
✅ کاملاً جا می‌شود. محاسبهٔ خالص، بدون I/O. کش در Django LocMem. جدول تعطیلات = دادهٔ نسخه‌دار در DB.

### نگهبان‌ها
- سال کبیسهٔ شمسی **الگوریتمی** محاسبه شود، نه جدول hardcode (الگوریتم ۳۳‌ساله با تصحیح).
- ورودی محدود به بازهٔ ۱۲۰۰–۱۵۰۰ شمسی؛ خارج از آن → پیام روشن، نه 500.
- تبدیل انبوه حداکثر ۱۰۰۰ خط.
- ارقام فارسی/انگلیسی/عربی هر سه پذیرفته شوند.

### حالت degraded
اگر API در دسترس نبود، **همان الگوریتم در TS سمت کلاینت** اجرا می‌شود (کد مشترک از طریق یک
بستهٔ منطقی). یعنی این ابزار **هرگز** از کار نمی‌افتد.

### تست پذیرش (اجباری، ≥ ۳)
1. `1403-12-30` → `2025-03-20` (آخرین روز سال کبیسه) — در هر دو جهت
2. ۱۵ روز کاری بعد از `1404-01-01` با تعطیلات ۱۴۰۴ → مقدار مورد انتظار مشخص
3. تبدیل انبوه ۱۰۰۰ خط در < ۲ ثانیه و بدون خطا
4. ورودی نامعتبر (`1404-13-01`) → پیام فارسی روشن، نه خطای خام
5. پارامترهای URL → وضعیت اولیه درست (رندر در SSR Static Bridge یکسان است)

### KPI
بازدید ماهانه · نرخ کپی‌کردن کد · نرخ اشتراک لینک · رتبه برای «تبدیل تاریخ شمسی»

## F-05 — JWT Debugger با تحلیل امنیتی

**مسیر:** `/fa/tools/jwt/` · **فاز ۲** · **تلاش: S** · ⭐ **پل ابزار ↔ برند امنیت**

### فرضیه
«jwt.io وجود دارد ولی انگلیسی است و **تحلیل امنیتی ندارد**. یک نسخهٔ فارسی که علاوه بر decode،
**هشدار امنیتی** بدهد، هم ابزار است هم ویترین دانش امنیت.»

### UI
- textarea برای paste کردن JWT
- **سه پنل:** Header · Payload · Signature
- Payload با **تاریخ‌های شمسی**: `exp` → «۱۴۰۴/۰۷/۱۵ ۱۴:۳۲ — ۳ روز پیش منقضی شده» + نوار زمان
- **پنل هشدارهای امنیتی** (این بخش متمایزکننده است):
  - `alg: none` → 🔴 بحرانی
  - الگوریتم متقارن با کلید عمومی منتشرشده → 🔴 (RS256→HS256 confusion)
  - `exp` گذشته → 🟠
  - فاصلهٔ `iat` تا `exp` بیش از ۲۴ ساعت → 🟡 (عمر طولانی)
  - نبود `iss` یا `aud` → 🟡
  - `kid` با مسیر/URL → 🔴 (path traversal / SSRF)
  - الگوریتم منسوخ (HS1، RS1) → 🟠
  - هر هشدار با **ارجاع به CWE** و یک جمله توضیح فارسی
- ⚠️ **هرگز verify واقعی انجام نمی‌شود مگر کاربر کلید بدهد.** و این صریح گفته می‌شود:
  «این ابزار فقط decode می‌کند. decode ≠ معتبر.»
- **بدون ارسال به سرور:** decode کاملاً سمت کلاینت است (این خودش یک پیام امنیتی است و باید نوشته شود)

### API
```
GET /api/v1/tools/jwt/analyze/?token=...  → { header, payload, warnings[] }
```
اختیاری — نسخهٔ اصلی سمت کلاینت است. اگر سمت سرور رفت، **token لاگ نمی‌شود.**

### cPanel
✅ محاسبهٔ خالص.

### نگهبان‌ها
- **لاگ نکردن token.** هیچ‌جا. نه access log، نه DB، نه analytics.
- token در URL قرار نگیرد (فقط POST یا پردازش کلاینت‌ساید).
- decode باید در برابر base64 malformed مقاوم باشد (بدون crash).
- اگر verify انجام شد: **الگوریتم باید از allowlist باشد**، نه از header توکن.

### تست پذیرش
1. یک JWT با `alg: none` → هشدار بحرانی صادر شود
2. توکن با `exp` گذشته → هشدار + نمایش تاریخ شمسی درست
3. base64 خراب → پیام روشن، نه exception
4. توکن معتبر ساختاری، بدون کلید → «decode شد، verify نشد» (نه «معتبر است»)
5. **assert: هیچ درخواست شبکه‌ای برای decode زده نمی‌شود**

### حالت degraded
این فیچر **به‌طور طراحی، کاملاً کلاینت‌ساید است** — یعنی «حالت degraded» عملاً حالت عادی آن است.
اگر endpoint اختیاری `/tools/jwt/analyze/` در دسترس نبود، هیچ تغییری در تجربهٔ کاربر ایجاد نمی‌شود.
تنها چیزی که از دست می‌رود «لینک اشتراک نتیجه» است که غیرفعال می‌شود — و این هم **عمداً** است،
چون token هرگز نباید سمت سرور برود تا قابل اشتراک شود. این تصمیم در UI توضیح داده می‌شود
(«برای محافظت از توکن شما، نتیجه فقط در مرورگر خودتان پردازش می‌شود») — که خودش یک پیام امنیتی است.

### KPI
استفادهٔ ماهانه · نرخ کلیک روی هشدارها (نشانهٔ ارزش آموزشی) · ارجاع از جامعهٔ امنیت

### UI
- ورودی دامنه + **checkbox اجباری** «مالک این دامنه هستم یا اجازه دارم» (بدون تیک، دکمه غیرفعال)
- **پیشرفت مرحله‌به‌مرحله** (چون cron-based است، با chunked polling §۵.۳):
  DNS → TLS → هدرها → کوکی‌ها → محتوا
- **نتیجه:** گرید کلی A–F + گرید هر بخش + نمرهٔ عددی
- **شش بخش بررسی:**
  1. **هدرهای امنیتی HTTP** — CSP، HSTS، X-Frame-Options، X-Content-Type-Options،
     Referrer-Policy، Permissions-Policy — هرکدام با وضعیت + توصیهٔ فارسی + snippet پیکربندی
  2. **TLS/SSL** — نسخهٔ پروتکل، کیفیت سوییت‌ها، وضعیت زنجیرهٔ گواهی، تاریخ انقضا (شمسی)
  3. **DNS** — SPF، DMARC، DKIM، CAA، DNSSEC، SOA
  4. **کوکی‌ها** — Secure، HttpOnly، SameSite
  5. **قرارگیری محتوا** — mixed content، منابع ثالث، فرم‌های بدون HTTPS
  6. **نشت اطلاعات** — سرور banner، نسخهٔ framework قابل تشخیص، مسیرهای عمومی حساس
- **کارت قابل اشتراک:** یک تصویر زیبا با گرید + دامنه + تاریخ شمسی (OG generator) + لینک دائمی `noindex`
- **خروجی PDF** (ساخته‌شده در CI/سرور با الگوی §۵.۳)
- **CTA در پایان گزارش:** «گزارش کامل + تست نفوذ واقعی» → **قیف PenTestor** (این هدف تجاری فیچر است)

### API
```
POST /api/v1/scanner/jobs/          { domain, consent: true }  → { job_id }
GET  /api/v1/scanner/jobs/<id>/poll/?offset=n                  → { state, steps[], result? }
GET  /api/v1/scanner/results/<result_id>/                      → گزارش عمومی (mask شده)
```

### cPanel (چطور در پاکت جا می‌شود) ⭐
اسکن شامل چند درخواست شبکه با timeout است → **می‌تواند از ۲۵ ثانیه بگذرد.** پس:
1. `POST` فقط یک **ردیف در جدول `ScanJob`** با وضعیت `pending` می‌سازد و `job_id` می‌دهد.
2. **cron هر دقیقه** management command `process_scan_jobs` را اجرا می‌کند:
   claim با `select_for_update` + `skip_locked`-like روی MariaDB، اجرای اسکن، ذخیرهٔ نتیجه.
3. کلاینت با **chunked polling** وضعیت را می‌پرسد.
4. هر مرحلهٔ اسکن timeout ≤ ۵ ثانیه دارد؛ کل اسکن ≤ ۹۰ ثانیه در پس‌زمینه.

این دقیقاً الگوی §۵.۳ است و **الگوی مرجع برای همهٔ کارهای پس‌زمینهٔ بعدی** خواهد بود.

### حالت degraded
اگر cron عقب است یا صف پر: پیام صادقانه «صف شلوغ است، نتیجه تا چند دقیقه دیگر» +
صفحهٔ **نتایج نمونه** (دامنه‌های عمومی معروف، از پیش اسکن‌شده) تا کاربر چیزی ببیند.

### تست پذیرش
1. اسکن یک دامنهٔ نمونهٔ کنترل‌شده → هر ۶ بخش نتیجه دارد و گرید محاسبه می‌شود
2. **assert: هیچ درخواستی به پورت غیر ۴۴۳/۸۰ زده نمی‌شود** (تست نگهبان ۱ — اجباری)
3. دامنهٔ blocklist‌شده → رد با پیام روشن، بدون اجرای اسکن
4. rate limit: درخواست ششم در یک ساعت → 429
5. `consent: false` → 400
6. نتیجهٔ عمومی mask شده است (assert نبود نسخهٔ دقیق سرویس‌دهنده)
7. `noindex` روی صفحهٔ نتیجه وجود دارد
8. polling با offset → گام‌های تکراری برنمی‌گرداند

### KPI
تعداد اسکن ماهانه · **نرخ اشتراک کارت** · نرخ تبدیل CTA به لید PenTestor · ترافیک ارگانیک

## F-08 — دستیار امت (RAG روی محتوای خودمان) ⭐

**مسیر:** `/fa/assistant/` + ویجت شناور · **فاز ۳** · **تلاش: L**

### فرضیه
«در بازاری که هر شرکتی ادعای AI دارد، یک دستیار که **روی محتوای واقعی خودمان** آموزش دیده،
**با ارجاع به منبع** جواب می‌دهد و وقتی نمی‌داند **می‌گوید نمی‌دانم**،
قوی‌ترین و صادقانه‌ترین دمویی است که می‌توان ساخت.»

### رفتار (این بخش از مدل مهم‌تر است)
1. **فقط** روی کورپوس خود امت جواب می‌دهد: Field Library · کیس‌استادی‌ها · ADRها · مستندات محصولات · FAQ.
2. **هر ادعا باید ارجاع داشته باشد** → `[۱]` با لینک به صفحهٔ منبع. بدون ارجاع = ادعا حذف می‌شود.
3. وقتی کورپوس جوابی ندارد: **«این را در مطالب ما پیدا نکردم»** + پیشنهاد مرتبط + لینک تماس.
   **هرگز** از دانش عمومی مدل جواب ندهد. (این قید سخت است و باید تست شود.)
4. فارسی پاسخ می‌دهد؛ اصطلاح فنی انگلیسی را در پرانتز می‌آورد.
5. صریح اعلام می‌کند: «این پاسخ توسط مدل زبانی از روی مطالب امت تولید شده و ممکن است خطا داشته باشد.»

### معماری RAG (بدون vector DB — الگوی §۵.۳)

```
CI / cron (نه درخواست کاربر):
  محتوا (Post, CaseStudy, ADR, FAQ)
    → chunk کردن (۴۰۰–۶۰۰ کاراکتر، هم‌پوشانی ۶۰)
    → embedding با provider انتزاعی (ADR-007)
    → ذخیره در جدول AssistantChunk: {id, source_type, source_id, url, text, embedding BLOB, hash}
    → فقط chunkهای تغییرکرده (hash) دوباره embedding می‌شوند

درخواست کاربر:
  POST /assistant/ask/ {question, session_id?}
    → job_id (بلافاصله، < ۲۰۰ms)
  worker (همان درخواست، چون سبک است):
    → embedding پرسش
    → numpy cosine روی همهٔ chunkها (n≈۵۰۰–۲۰۰۰، < ۵۰ms)
    → top-6 با آستانهٔ شباهت
    → اگر هیچ‌کدام بالای آستانه نبود → پاسخ «نمی‌دانم» (بدون تماس با LLM = صرفه‌جویی)
    → prompt با context + دستور سخت «فقط از متن داده‌شده؛ اگر نیست بگو نیست»
    → LLM provider (ADR-007)
    → ذخیرهٔ پاسخ در AssistantAnswer (برای polling)
  GET /assistant/ask/<id>/poll/?offset=n   (هر ۷۰۰ms)
```

⭐ **نکتهٔ طراحی مهم:** آستانهٔ شباهت **قبل از** تماس با LLM اعمال می‌شود.
این هم هزینه را کم می‌کند هم از توهم‌سازی جلوگیری می‌کند. یک تصمیم مهندسی که باید در `docs/AI-OPS.md` مستند شود.

### UI
- چت با streaming تدریجی (از polling)
- **هر پاسخ با چیپ‌های منبع** → کلیک = رفتن به صفحه
- پیشنهادهای آماده: «PenTestor چطور کار می‌کند؟» · «روی چه پشته‌ای کار می‌کنید؟» · «یک کیس‌استادی امنیتی بگو»
- دکمهٔ «این پاسخ مفید بود؟» → سیگنال کیفیت (لاگ تجمیعی، بدون متن)
- **نمایش شفاف:** یک دکمهٔ «چه چیزی پیدا شد؟» که chunkهای بازیابی‌شده را نشان می‌دهد.
  این یعنی Show Your Work برای RAG — و برای مخاطب فنی فوق‌العاده جذاب است.

### cPanel
- **embedding:** cron هر شب روی محتوای تغییرکرده (نه در درخواست کاربر).
- **جست‌وجو:** numpy در حافظه، < ۵۰ms. بدون Redis، بدون pgvector.
- **LLM:** تماس HTTPS بیرونی (استثنای ۱ در §۵.۵).
- **پاسخ:** chunked polling (ADR-008). **بدون WebSocket.**

### API
```
POST /api/v1/assistant/ask/
     { question, session_id?, consent_to_log?: false }
     → 202 { job_id }                              # < 200ms، بدون انتظار
GET  /api/v1/assistant/ask/<job_id>/poll/?offset=n
     → 200 { state, progress[], answer?, citations[], offset_next, mode }
                                                     # mode: "llm" | "bm25"
GET  /api/v1/assistant/suggestions/                 # پرسش‌های پیشنهادی (کش‌شونده)
POST /api/v1/assistant/feedback/  { answer_id, helpful }   # فقط سیگنال، بدون متن
```

- `citations[]` = `{ url, title, chunk_id }` — **اگر خالی باشد، پاسخ نمایش داده نمی‌شود.**
- `mode` به کلاینت می‌گوید پاسخ از LLM آمده یا BM25 — تا پیام صادقانهٔ درست نشان داده شود.
- **هیچ WebSocket نیست** — الگوی chunked polling (ADR-008، §۵.۳).

### نگهبان‌ها (اجباری)
سقف هزینهٔ روزانه از پیکربندی (رسیدن به سقف → fallback BM25، نه خطا) ·
کش پاسخ در DB بر اساس hash پرسش نرمال‌شده ·
rate limit ۲۰/ساعت بر IP + هانی‌پات ·
حداکثر ورودی ۵۰۰ کاراکتر ·
**عدم لاگ کردن متن پرسش کاربر** مگر با رضایت صریح (checkbox) ·
اعلام صریح AI بودن در هر پاسخ ·
فیلتر خروجی: اگر پاسخی ارجاع نداشت، **نمایش داده نمی‌شود** و «نمی‌دانم» جایگزین می‌شود.

### حالت degraded (باید تست شود — این بخش مهم‌تر از حالت خوش‌بینانه است)
وقتی provider در دسترس نیست یا سقف هزینه پر شده:
**جست‌وجوی BM25 روی همان کورپوس** + پاسخ قالبی صادقانه:
«پاسخ هوشمند موقتاً در دسترس نیست. این مطالب مرتبط را پیدا کردیم: [۳ لینک]»
کاربر **هرگز** spinner بی‌پایان یا خطای خام نمی‌بیند.

### تست پذیرش
1. پرسش با جواب موجود در کورپوس → پاسخ **با حداقل یک ارجاع معتبر** (assert لینک وجود دارد)
2. پرسش بی‌ربط کامل → «پیدا نکردم» + **assert هیچ تماسی با LLM زده نشد** (صرفه‌جویی)
3. **provider خاموش → fallback BM25 کار می‌کند و پیام صادقانه نشان داده می‌شود** (تست اجباری)
4. نرخ limit: درخواست ۲۱ام در ساعت → 429 با پیام فارسی
5. polling با offset → متن تکراری برنمی‌گردد
6. پاسخ بدون ارجاع → نمایش داده نمی‌شود (تست منطق فیلتر)
7. هر پاسخ شامل اعلام AI بودن است

### KPI
تعداد پرسش · **درصد پرسش‌هایی که ارجاع داشتند** (معیار کیفیت RAG) · نرخ «مفید بود» · هزینه به ازای پرسش

## الگوی مشترک همهٔ ابزارها (اجباری)

هر ابزار در `web/src/features/toolbox/<name>/` این‌ها را دارد:

```
<name>/
├── index.tsx          # صفحه با useSEO + JSON-LD
├── Tool.tsx           # UI
├── logic.ts           # ⭐ منطق خالص، بدون DOM — مشترک بین سرور و کلاینت
├── logic.test.ts      # تست منطق (این مهم‌ترین فایل است)
├── Tool.e2e.ts        # تست e2e در fa و en
└── meta.ts            # slug, slugs_fa, title, description, JSON-LD schema
```

**قوانین مشترک:**
1. **منطق در `logic.ts` و بدون DOM** — تا هم سمت سرور (Static Bridge) هم کلاینت اجرا شود.
2. **همهٔ ابزارها lazy-load** — هیچ‌کدام در bundle اولیه نیستند.
3. **هر ابزار یک `?`-URL-state دارد** — وضعیت در URL بازتاب می‌شود تا قابل اشتراک باشد.
4. **هر ابزار خروجی قابل اشتراک دارد** — حداقل یک لینک دائمی.
5. **هر ابزار یک بخش «چطور کار می‌کند» دارد** با کد واقعی (G1).
6. **هر ابزار در `low-power` کامل کار می‌کند** — فقط جلوه‌ها حذف می‌شوند، نه کارکرد.
7. **هر ابزار در هر دو زبان کامل است** — گیت `content:check`.
