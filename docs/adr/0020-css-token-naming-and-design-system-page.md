# ADR-0020: الگوی نام‌گذاری توکن CSS (جلوگیری از self-reference) و صفحهٔ Design System به‌جای Storybook

**وضعیت:** پذیرفته‌شده

## زمینه

این ADR دو تصمیم کوچک‌تر اما به‌هم‌مرتبط فاز ۳ را مستند می‌کند که هر دو دربارهٔ «چگونه توکن‌ها/کامپوننت‌ها در عمل مصرف و نمایش داده شوند» هستند.

### بخش ۱: باگ تکراری self-reference در `@theme inline`

در پیاده‌سازی اولیهٔ `globals.css`، دو بار یک الگوی باگ یکسان رخ داد:

1. **شعاع/سایه:** `:root` مقدار خام را مستقیماً با همان نامی تعریف کرده بود که `@theme inline` به‌عنوان توکن نهایی Tailwind می‌خواست (مثلاً `--radius-sm` در `:root` و دوباره `--radius-sm: var(--radius-sm)` در `@theme inline`) → ارجاع به خودش، مقدار `unset`/نامعتبر.
2. **فونت مونو:** متغیر next/font برای JetBrains Mono نیز `--font-technical` نام‌گذاری شده بود، درحالی‌که `@theme inline` همان نام را به‌عنوان توکن تایپوگرافی تعریف می‌کرد → دقیقاً همان الگوی باگ شماره ۱، این‌بار در لایهٔ فونت.

هر دو باگ فقط با بررسی دستی مقدار نهایی computed style در مرورگر کشف شدند (نه با خطای build؛ Tailwind v4 self-reference را silently به مقدار نامعتبر resolve می‌کند).

### بخش ۲: Storybook در برابر صفحهٔ دمو

بریف فاز ۳ «Storybook یا صفحهٔ نمونه» را به‌عنوان دو گزینهٔ هم‌ارز برای مستندسازی بصری Design System مطرح کرده بود.

## تصمیم

### بخش ۱: قرارداد نام‌گذاری `-value-`/`-raw`

هر متغیر CSS خامی که **منبع مقدار** یک توکن نهایی Tailwind است (نه خودِ توکن) باید نامی با پسوند متمایز داشته باشد، هرگز هم‌نام با کلید نهایی در `@theme`:

- مقادیر خام شعاع/سایه در `:root`: پسوند `-value-` (مثلاً `--radius-value-sm`, `--shadow-value-glow-cta`). نگاشت در `@theme inline`: `--radius-sm: var(--radius-value-sm);`.
- متغیر خروجی `next/font`/فونت خام: پسوند `-raw` (مثلاً `--font-technical-raw: "JetBrains Mono";`). نگاشت در `@theme inline`: `--font-technical: var(--font-technical-raw), ui-monospace, monospace;`.

قاعدهٔ کلی: **یک نام CSS variable هرگز نباید هم در `:root` به‌عنوان مقدار خام و هم در `@theme`/`@theme inline` به‌عنوان توکن نهایی ظاهر شود.** رنگ‌ها از این قاعده مستثنی نیستند عملاً — بلکه از ابتدا با نام متفاوت تعریف شده بودند (`--background` در `:root` در برابر `--color-background` در `@theme inline`)، که چرا این دو باگ فقط در radius/shadow/font رخ داد نه در رنگ.

### بخش ۲: صفحهٔ Design System به‌جای Storybook

`frontend/src/app/[locale]/design-system/page.tsx` ساخته شد: یک صفحهٔ واقعی Next.js (در هر دو locale در دسترس: `/design-system` فارسی، `/en/design-system` انگلیسی) که رنگ‌ها، تایپوگرافی، فاصله، تمام variantهای دکمه (شامل حالت loading/disabled)، فرم (FormGroup+Input)، badge، avatar، کارت‌ها (یکی با Skeleton)، و نمونهٔ واقعی `formatDate`/`formatToday`/`formatNumber` را نمایش می‌دهد.

**Storybook به‌طور آگاهانه انتخاب نشد**، به دلایل زیر:

1. Storybook یک وابستگی build/dev-tooling قابل‌توجه (پیکربندی جداگانه، addon، build pipeline مجزا) اضافه می‌کرد که باید جداگانه روی هاست اشتراکی cPanel نگه‌داری/دیپلوی می‌شد (یا کلاً از production جدا نگه داشته می‌شد) — برای این فاز که صرفاً به یک مرجع بصری نیاز داشت، این هزینه توجیه نداشت (قانون ۶).
2. یک صفحهٔ Next.js واقعی دقیقاً همان محیط رندر (فونت‌ها، CSS توکن‌ها، `next-intl`، `next-themes`) را استفاده می‌کند که صفحات واقعی سایت استفاده می‌کنند — یعنی خودش یک تست دود end-to-end برای کل سیستم طراحی است؛ Storybook با iframe/webpack جدا، این تضمین یکپارچگی را به‌صورت خودکار نمی‌دهد.
3. صفحهٔ دمو به‌صورت طبیعی هر دو زبان/جهت (RTL/LTR) و هر دو تم (روشن/تاریک، چون از همان `ThemeProvider` واقعی استفاده می‌کند) را نمایش می‌دهد، که دقیقاً نیاز اصلی این پروژهٔ دوزبانه بود.

## دلیل

- الگوی `-value-`/`-raw` یک قانون مکانیکی و قابل‌پیروی است که از تکرار این باگ خاص (که دوبار در همین فاز رخ داد) در فازهای بعد جلوگیری می‌کند؛ مستندسازی آن (نه فقط رفع سکوتی) اهمیت دارد چون باگ هیچ خطای build/type تولید نمی‌کند.
- صفحهٔ دمو، با هزینهٔ تقریباً صفر (فقط یک صفحهٔ React دیگر در همان اپ)، پوشش مستندسازی لازم را فراهم کرد بدون افزودن ابزار جدید که نیاز به نگه‌داری/دیپلوی جداگانه دارد.

## پیامدها

- هر PR آینده که یک توکن CSS خام جدید به `:root` اضافه می‌کند، باید در بازبینی کد بررسی شود که نامش با کلید معادل در `@theme inline` تداخل نداشته باشد (پسوند `-value-`/`-raw` یا معادل آن را رعایت کند).
- اگر در آینده نیاز واقعی به مستندسازی تعاملی سطح-کامپوننت (مثل تغییر زندهٔ props در UI) پیدا شد که صفحهٔ دمو ساده پاسخگو نیست، این تصمیم باید بازبینی و احتمالاً Storybook/Ladle به‌عنوان ADR جداگانه اضافه شود — این ADR فقط برای وضعیت فعلی (فاز ۳) معتبر است، نه یک رد دائمی Storybook.
- صفحهٔ `/design-system` باید با هر atom/molecule/organism جدیدی که فازهای بعد اضافه می‌کنند، به‌روزرسانی شود تا مرجع بصری کامل بماند.
