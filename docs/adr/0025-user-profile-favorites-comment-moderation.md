# ADR-0025: دامنهٔ پروفایل کاربر (علاقه‌مندی‌ها/تاریخچه) و مدیریت (moderation) کامنت

**وضعیت:** پذیرفته‌شده

## زمینه

بریف فاز ۴ (آیتم ۷) «پروفایل کاربر، تاریخچه، علاقه‌مندی‌ها، کامنت‌ها با moderation» را خواسته، بدون تعریف دقیق «تاریخچه» یعنی چه. `ARCHITECTURE.md` فاز ۱ صراحتاً فرض کرده بود که در فاز اول **هیچ مدل `Enrollment`** (ثبت‌نام واقعی در دوره) وجود ندارد — محتوای Academy «آزاد و عمومی» است. این یعنی «تاریخچه» نمی‌تواند به‌معنای «دوره‌های خریداری‌شده» باشد. برای جلوگیری از توقف کار روی این ابهام جزئی (که ارزش یک پرسش جداگانه از مالک محصول را نداشت)، طبق الگوی «فرضیات مستندشده» بخش ۹ `ARCHITECTURE.md`، این ADR یک تصمیم مستند و قابل‌تغییر ثبت می‌کند.

## تصمیم

### دامنهٔ پروفایل (فاز ۴)

- **علاقه‌مندی‌ها (Favorites):** مدل عمومی `accounts.Favorite` با `GenericForeignKey` (`user`, `content_type`, `object_id`, `created_at`؛ `unique_together=(user, content_type, object_id)`) — کاربر می‌تواند `Service`/`Project`/`Course`/`BlogPost` را بوک‌مارک کند. انتخاب GenericForeignKey (به‌جای ۴ جدول M2M جدا) چون منطق/API/UI «افزودن به علاقه‌مندی‌ها» برای هر ۴ نوع محتوا کاملاً یکسان است.
- **تاریخچه:** به‌معنای «فهرست کامنت‌های نوشته‌شده توسط کاربر» (از طریق رابطهٔ موجود `Comment.author`) + «فهرست علاقه‌مندی‌ها»، **نه** تاریخچهٔ خرید/ثبت‌نام (که در فاز اول اصلاً مدل ندارد، طبق فرض `ARCHITECTURE.md`). اگر در آینده `Enrollment` اضافه شود، این بخش از پروفایل باید گسترش یابد.
- بدون مدل «تاریخچهٔ بازدید صفحات» (view history) در این فاز — نیاز به زیرساخت ردیابی رفتار کاربر دارد که خارج از scope «ویترین» تعریف‌شده در مأموریت پروژه است و با حریم خصوصی/GDPR-like بدون سیاست مشخص تداخل می‌کند.

### Moderation کامنت

- **از طریق Django Admin**، نه یک داشبورد اختصاصی Next.js. دلیل: تمام محتوای دیگر پروژه (Service/Project/Course/BlogPost/...) همین الان از طریق ادمین مدیریت می‌شود؛ ساخت یک داشبورد مدیریت جداگانه فقط برای کامنت، وابستگی/سطح حمله/هزینهٔ نگه‌داری اضافه بدون سود متناسب برای این مقیاس ایجاد می‌کند.
- یک admin action سفارشی (`approve_comments`, `reject_comments`) روی `CommentAdmin` برای تأیید/رد دسته‌جمعی.
- API عمومی فقط کامنت‌های `status="approved"` را در لیست یک پست برمی‌گرداند؛ کاربر واردشده کامنت خودش (حتی `pending`) را هم در پاسخ `my_comments`/پروفایل می‌بیند (شفافیت برای کاربر دربارهٔ وضعیت کامنتش).

## دلیل

- محدودکردن «تاریخچه» به داده‌ای که واقعاً در مدل داده موجود/برنامه‌ریزی‌شده است (کامنت + علاقه‌مندی)، به‌جای حدس‌زدن یک مدل جدید کامل (Enrollment/Purchase History) که با تصمیم صریح فاز ۱ («بدون Enrollment») در تضاد بود.
- استفاده از Django Admin برای moderation، زمان توسعه را برای فیچری که فرکانس استفادهٔ پایین (تیم محتوا/ادمین، نه کاربر نهایی) دارد، به نفع فیچرهای با اولویت بالاتر (صفحات محتوایی اصلی) صرفه‌جویی می‌کند؛ قانون ۴ («کیفیت > سرعت») نقض نمی‌شود چون ادمین Django خودش یک رابط کامل، امن، و تست‌شده (توسط Django core) است — نه یک میان‌بر بی‌کیفیت.

## پیامدها

- اگر در فازهای بعد `Enrollment` اضافه شود، پروفایل باید بخش «دوره‌های من» را اضافه کند؛ این ADR باید در آن زمان بازبینی شود.
- اگر حجم moderation کامنت در آینده آنقدر زیاد شود که ادمین Django کافی نباشد (مثلاً نیاز به workflow چندمرحله‌ای/چند نقشی)، باید ADR جدیدی برای یک سامانهٔ moderation اختصاصی نوشته شود.
