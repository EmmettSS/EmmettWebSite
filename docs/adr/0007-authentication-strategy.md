# ADR-0007: استراتژی احراز هویت و مدل User سفارشی

**وضعیت:** پذیرفته‌شده

## زمینه

نیاز به حساب کاربری واقعی برای دانشجویان Academy و مشتریان تأیید شده است. باید روش احراز هویت، مدل User، و جداسازی شناسهٔ داخلی/عمومی برای جلوگیری از افشای اطلاعات (IDOR) طراحی شود.

## گزینه‌ها برای روش احراز هویت

1. **ایمیل + رمز عبور استاندارد Django:** ساده‌ترین، کم‌ریسک‌ترین، بدون وابستگی به سرویس پیامکی خارجی برای جریان حیاتی ورود.
2. **شماره موبایل + OTP (Kavenegar):** تجربهٔ رایج کاربر ایرانی، ولی وابستهٔ ورود به در دسترس‌بودن سرویس پیامکی خارجی (نقطهٔ شکست اضافه برای یک فرایند حیاتی امنیتی).
3. **هر دو:** پیچیدگی مدل/UX بیشتر در فاز اول.

## تصمیم

**گزینهٔ ۱ (ایمیل + رمز عبور)** برای فاز اول، طبق تأیید صریح مالک محصول. فیلد `phone` روی مدل `User` از همین حالا وجود دارد (nullable) تا بدون migration بزرگ در آینده، قابلیت ورود/تأیید پیامکی (یا صرفاً اعلان‌رسانی از طریق Kavenegar طبق `DISCOVERY.md`) اضافه شود.

## دلیل

- کمترین نقطهٔ شکست برای جریان حیاتی احراز هویت؛ سرویس پیامکی خارجی (Kavenegar) در فاز اول فقط برای **اعلان‌رسانی** (نه ورود) استفاده می‌شود؛ درصورت قطعی سرویس پیامکی، ورود کاربران مختل نمی‌شود.
- پیاده‌سازی استاندارد Django Auth (`AbstractUser` + `django-rest-framework` session/token) بالغ، امن (hashing، throttling آماده) و کم‌ریسک است.
- مدل User از ابتدا برای افزودن OTP در آینده آماده طراحی شده (فیلد `phone`, `is_phone_verified`) — بدون بدهی فنی.

## مدل User

`User(AbstractUser)`:
- `email` → `USERNAME_FIELD`, یکتا، اجباری
- `username` حذف می‌شود (ایمیل جایگزین آن است) — کاهش سطح حمله و سردرگمی کاربر
- `phone` → nullable، برای توسعهٔ آینده
- `role` → Enum (`admin`, `editor`, `student`, `client`) — کنترل دسترسی نقش‌محور ساده (RBAC سبک، نه سیستم مجوز پیچیده)
- `is_phone_verified` → bool، پیش‌فرض False

## جلوگیری از IDOR (قانون ۱۶)

تمام مدل‌های منتشرشده در API عمومی (`Project`, `Course`, `BlogPost`, `Contact`, `Lead`, `AIRequest`, ...) علاوه بر PK عددی داخلی (`id`, برای کارایی join/ایندکس داخلی)، یک `public_id = UUIDField(default=uuid4, unique=True, db_index=True)` دارند. تمام URLهای API و فرانت از `public_id` استفاده می‌کنند؛ `id` عددی هرگز در پاسخ API یا URL عمومی افشا نمی‌شود — جلوگیری از حدس‌پذیری شناسه و شمارش رکوردها (enumeration attack).

## پیامدها

- احراز هویت DRF باید هم Session (برای SSR/Next.js که روی همان دامنه یا ساب‌دامنه پروکسی می‌شود) و هم امکان Token/JWT برای مصرف‌کنندگان آینده (موبایل) را پشتیبانی کند؛ انتخاب دقیق مکانیزم (`SessionAuthentication` + `CSRF` در مقابل `SimpleJWT`) در فاز Implementation امنیت با توجه به معماری CORS نهایی تصمیم‌گیری می‌شود.
- رمزهای عبور طبق استاندارد Django (`PBKDF2`/`Argon2`) هش می‌شوند؛ هرگز متن ساده ذخیره نمی‌شود.
- افزودن OTP در آینده نیازمند یک مدل کوچک جدید (`OTPCode`) در `accounts` خواهد بود، نه تغییر در مدل `User`.
