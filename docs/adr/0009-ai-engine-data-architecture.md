# ADR-0009: معماری دادهٔ اپ ai_engine و Guardrail فرهنگی

**وضعیت:** پذیرفته‌شده

## زمینه

قوانین ۱۲ تا ۱۴ سه الزام سخت‌گیرانه دارند:
- قانون ۱۲: تمام فیچرهای AI فقط از طریق اپ `ai_engine`؛ تماس مستقیم با مدل از اپ‌های دیگر ممنوع.
- قانون ۱۳: ورودی کاربر به موتور AI فقط از لیست‌های بستهٔ Enum/Choice — هرگز free-text.
- قانون ۱۴: هر فیچر AI باید «Guardrail فرهنگی ایرانی» داشته باشد.

دو فیچر تأییدشده برای فاز اول: (الف) دستیار کشف نیاز مشتری (Enum-based)، (ب) ابزار کمک‌محتوا برای Library/Academy.

## گزینه‌ها برای مرزبندی دسترسی به AI

1. **هر اپ مستقیماً SDK مدل (OpenAI و...) را import و صدا بزند:** سریع‌تر برای توسعه ولی قانون ۱۲ را مستقیماً نقض می‌کند و امکان اعمال یکپارچهٔ Guardrail/حسابرسی/Rate-limit را از بین می‌برد.
2. **تمام فراخوانی‌ها از طریق یک سرویس مرکزی در `ai_engine` (الگوی Facade/Gateway):** اپ‌های دیگر (`leads`, `blog`, `academy`) فقط به یک تابع سرویس سطح‌بالا در `ai_engine.services` دسترسی دارند (مثلاً `run_lead_discovery(enum_input) -> AISuggestion`)؛ هیچ import مستقیمی از SDK مدل در اپ‌های دیگر مجاز نیست.

## تصمیم

**گزینهٔ ۲.** معماری Gateway/Facade: اپ `ai_engine` تنها نقطهٔ ورودی به هر مدل زبانی است.

## دلیل

- اجرای فنی قانون ۱۲ در سطح معماری (نه فقط توافق تیمی) — Code Review می‌تواند با یک قاعدهٔ import-linter این مرز را خودکار بررسی کند.
- امکان اعمال متمرکز Guardrail، Rate Limiting، لاگ‌گیری/Audit، و مدیریت هزینهٔ فراخوانی مدل در یک‌جا.
- جایگزینی ارائه‌دهندهٔ مدل (OpenAI ↔ سایر) در آینده فقط به تغییر یک adapter داخل `ai_engine` نیاز دارد، نه تغییر در اپ‌های مصرف‌کننده.

## طراحی اجرای Enum-only (قانون ۱۳)

هر فیچر AI یک **اسکیمای ورودی بسته** از پیش تعریف‌شده دارد (نه یک پیام متنی آزاد):

```
LeadDiscoveryInput:
  project_type: Enum[software, ai_ml, cybersecurity, product_design, infrastructure, other]
  budget_range: Enum[under_10k, 10k_50k, 50k_200k, over_200k, not_sure]
  timeline: Enum[asap, 1_3_months, 3_6_months, exploring]
  company_size: Enum[solo, small_team, sme, enterprise]
```

ورودی کاربر هرگز به‌صورت رشتهٔ آزاد وارد `AIRequest.input_payload` نمی‌شود؛ هر مقدار باید عضو یک `choices` ثبت‌شده در بک‌اند باشد و DRF Serializer قبل از رسیدن به `ai_engine` آن را اعتبارسنجی می‌کند (رد درخواست با مقدار خارج از Enum، نه پاس‌دادن آن به مدل).

خروجی مدل (`AISuggestion.output_payload`) نیز **قالب‌محور (templated)** است، نه متن خام نمایش داده‌شده به کاربر بدون پالایش — مدل فقط می‌تواند بین مقادیر از پیش تعریف‌شده در خروجی انتخاب/امتیازدهی کند (مثلاً «بهترین سرویس پیشنهادی از بین ۵ سرویس موجود» + یک خلاصهٔ کوتاه تولیدشده از قالب ثابت)، تا ریسک خروجی نامناسب/خارج از برند به حداقل برسد.

## طراحی Guardrail فرهنگی (قانون ۱۴)

مدل `GuardrailRule` (دیتابیسی، نه کد ثابت) امکان تعریف قواعد زیر را بدون نیاز به دیپلوی فراهم می‌کند:
- `keyword_blocklist`: فهرست کلمات/موضوعات ممنوعه (سیاسی، مذهبی حساس، محتوای نامناسب فرهنگی).
- `cultural_sensitivity`: قواعد لحن/ادب مناسب فرهنگ ایرانی (مثلاً عدم استفاده از زبان غیررسمی بیش‌ازحد در ارتباط B2B، رعایت احترام در خطاب).
- `topic_restriction`: محدودسازی موضوعی خروجی فقط به دامنهٔ کسب‌وکار امیت (جلوگیری از «کشیده‌شدن» مدل به موضوعات نامرتبط).

هر `AIRequest` پیش از رسیدن به مدل زبانی و بعد از دریافت خروجی، از یک لایهٔ بررسی Guardrail عبور می‌کند (pre-check روی input_payload، post-check روی output_payload)؛ موارد trigger‌شده در `AISuggestion.guardrail_flags` ثبت و (در صورت severity بالا) درخواست با وضعیت `blocked_by_guardrail` متوقف و برای بازبینی انسانی علامت‌گذاری می‌شود — نه نمایش مستقیم به کاربر.

## مدیریت پرامپت (`PromptTemplate`)

پرامپت‌های سیستمی هر فیچر در جدول `PromptTemplate` (نه hard-code در کد پایتون) نگه‌داری می‌شوند تا تیم بتواند لحن/دستورالعمل را بدون دیپلوی به‌روزرسانی و نسخه‌بندی کند. فاز اول Implementation می‌تواند با یک رکورد پیش‌فرض برای هر فیچر شروع شود؛ طراحی schema از روز اول این قابلیت را پشتیبانی می‌کند.

## پیامدها

- هرگونه PR که در اپی غیر از `ai_engine` مستقیماً SDK مدل زبانی را import کند، باید در Code Review رد شود (قاعدهٔ معماری سخت).
- کلید API ارائه‌دهندهٔ مدل فقط در `.env` و فقط توسط `ai_engine` خوانده می‌شود (قانون ۵).
- هزینهٔ هر فراخوانی باید لاگ شود (`AIRequest.latency_ms`, متادیتای مصرف توکن در صورت در دسترس بودن از provider) تا امکان مانیتورینگ هزینه وجود داشته باشد.
- تعریف دقیق enum های هر فیچر و قواعد اولیهٔ Guardrail باید قبل از Implementation اپ `ai_engine` با مالک محصول نهایی شود (در فاز Implementation مربوطه دوباره به‌صورت سؤالات مشخص مطرح می‌شود).
