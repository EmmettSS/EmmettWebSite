# ADR-0003: استراتژی i18n سه‌لایه — gettext + django-modeltranslation + Translation پویا

**وضعیت:** پذیرفته‌شده

## زمینه

قانون ۹ می‌گوید: «تمام متن‌های UI در فایل‌های ترجمه (gettext) باشند؛ هیچ رشته hard-code شده نداشته باشیم.» اما این قانون دربارهٔ **متن ثابت رابط کاربری** است، نه دربارهٔ **محتوای پویای دیتابیس‌محور** (عنوان یک Project، توضیح یک Course، متن یک مقاله). این دو مسئله ماهیتاً متفاوت‌اند و نیاز به دو راهکار متفاوت دارند؛ همچنین مالک محصول نیاز به یک لایهٔ سوم (رشته‌های CMS-محور قابل‌ویرایش بدون دیپلوی) را تأیید کرد.

## گزینه‌ها برای محتوای مدل‌محور

1. **`django-modeltranslation`:** فیلد `title` در مدل به‌صورت خودکار به `title_fa`/`title_en` تبدیل می‌شود (ستون‌های اضافه در همان جدول). ادغام عالی با Django Admin (تب‌های زبان روی همان فرم)، کوئری ساده (بدون JOIN اضافه)، مناسب برای تعداد زبان ثابت و کم (اینجا دقیقاً ۲ زبان).
2. **`django-parler`:** جدول ترجمهٔ جدا به‌ازای هر مدل (`ModelTranslation`)؛ مناسب‌تر برای تعداد زبان زیاد/پویا، ولی هر کوئری نیاز به JOIN اضافه دارد و پیچیدگی ORM بیشتری ایجاد می‌کند.
3. **فیلدهای دستی دوزبانه بدون پکیج خارجی:** کمترین وابستگی (قانون ۶) ولی تکرار کد دستی برای هر فیلد/مدل، بدون ادغام آمادهٔ ادمین.

## تصمیم

برای محتوای مدل‌محور: **`django-modeltranslation`** (مطابق تأیید صریح مالک محصول).
برای متن ثابت UI: **gettext استاندارد Django** (`.po`/`.mo`) در بک‌اند + سیستم پیام هم‌ساختار در Next.js (`next-intl` یا معادل سبک) در فرانت.
برای رشته‌های CMS-محور پویا: مدل `core.Translation` (کلید `namespace + key + locale`)، ویرایش‌پذیر در ادمین، کش‌شده طبق `ADR-0006`.

## دلیل

- تعداد زبان‌های پروژه **ثابت و برابر ۲** است (fa/en) و در آیندهٔ نزدیک تغییر نمی‌کند؛ بنابراین هزینهٔ اضافی schema پویای `django-parler` (جدول/JOIN اضافه برای هر مدل) توجیهی ندارد و `django-modeltranslation` سادگی و کارایی بیشتری می‌دهد (قانون ۱۵: بهینگی کوئری).
- ادغام `django-modeltranslation` با Django Admin از پیش آماده است (ویجت تب‌دار)، که هزینهٔ ساخت پنل مدیریت محتوا را به‌شدت کاهش می‌دهد.
- gettext برای UI ثابت باقی می‌ماند چون این متن‌ها در کد (قالب/کامپوننت) زندگی می‌کنند، نه در دیتابیس؛ مخلوط‌کردن آن‌ها با مدل‌ها نقض اصل تفکیک مسئولیت است.
- جدول `Translation` پویا پاسخ به نیاز واقعی کسب‌وکار است: تیم بازاریابی/محتوا باید بتواند بدون دخالت توسعه‌دهنده و بدون دیپلوی، متن‌های کمپینی/بنری را ویرایش کند؛ gettext نیازمند کامپایل مجدد `.mo` و دیپلوی است، بنابراین برای این مورد مناسب نیست.

## پیامدها

- هر مدل جدید با محتوای چندزبانه باید فیلدهای ترجمه‌پذیرش را صریحاً در `translation.py` همان اپ ثبت کند (`TranslationOptions`)؛ فراموشی این مرحله باعث نمایش فقط یک زبان می‌شود — باید در Code Review چک شود (چک‌لیست PR).
- افزودن زبان سوم در آینده (در صورت نیاز) هزینهٔ migration دارد (ستون جدید برای هر فیلد ترجمه‌پذیر در تمام مدل‌ها) — ریسک پذیرفته‌شده چون تعداد زبان طبق مأموریت پروژه ثابت است.
- باید یک ابزار (management command) برای استخراج/همگام‌سازی کلیدهای gettext بین بک‌اند و فرانت نوشته شود تا دو سیستم ترجمهٔ UI دچار واگرایی نشوند.
- وابستگی جدید اضافه می‌شود: `django-modeltranslation` (توجیه: کتابخانهٔ بالغ، نگهداری‌شده، بدون وابستگی سنگین اضافه، دقیقاً حل‌کنندهٔ یک نیاز صریح پروژه — مطابق قانون ۶).
