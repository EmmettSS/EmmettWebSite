# ADR-0042: انیمیشن ورودی hero با CSS (نه JS) و ممنوعیت شروع محتوا از `opacity: 0`

**وضعیت:** پذیرفته‌شده — پس از شکست واقعی گیت Lighthouse روی `main` (2026-11-02)<br>
**تاریخ:** 2026-11-02<br>
**دامنه:** `frontend/src/components/ui-port/hero.tsx`، `frontend/src/app/globals.css`،
`frontend/src/components/ui-port/hero.test.tsx`، `frontend/scripts/verify-rendering.mjs`<br>
**مرتبط با:** ADR-0032 (بودجهٔ کارایی)، ADR-0037 (Lighthouse در CI)، ADR-0041 (pre-render/ISR)<br>
**تصمیم‌گیرندگان:** مالک محصول + ایجنت ارشد توسعه

## ۱. زمینه

پس از merge شدن ADR-0041، اجرای `main`
([`41399449660`](https://github.com/EmmettSS/EmmettWebSite/actions/runs/41399449660)) در گام
`Lighthouse CI` قرمز شد. annotation تولیدشده (پس از اصلاح همین خط لوله در PR #7) دقیقاً این را گفت:

```
Lighthouse /en :: performance=0.93 ← largest-contentful-paint(w=25,s=0.84,1.4 s)
                                     speed-index(w=10,s=0.70,1.8 s)
                                     first-contentful-paint(w=10,s=0.99,0.6 s)
```

بودجه ۰٫۹۵ است؛ `/en` روی ۰٫۹۳ ایستاد و پنج URL دیگر سبز بودند.

### ۱-۱. ریشهٔ واقعی (نه حدس)

FCP = ۰٫۶s اما LCP = ۱٫۴s؛ یعنی «بزرگ‌ترین عنصر» ۰٫۸ ثانیه دیرتر از بقیهٔ صفحه دیده می‌شد.
این فاصله دقیقاً به یک الگوی کد در `hero.tsx` می‌خورد: کامپوننت کلاینتی با
`motion/react` و `initial={{ opacity: 0 }}`.

Next.js استایل اولیهٔ `motion` را در **HTML پخته‌شده** می‌نویسد. بررسی مستقیم خروجی بیلد:

```html
<!-- .next/server/app/en.html — پیش از اصلاح -->
<h1 class="text-[clamp(2.8rem,7vw,6.5rem)] …" style="opacity:0;transform:translateY(20px)">
  We engineer<br/><span>intelligent</span><br/>systems.
</h1>
```

یعنی بزرگ‌ترین متن صفحه — همان عنصری که LCP را می‌سازد — **در HTML ارسالی نامرئی** بود و فقط
پس از دانلود JS، hydration، ۸۰ms تأخیر و ۷۰۰ms فید ظاهر می‌شد. جمع این‌ها ≈ ۰٫۶ + ۰٫۰۸ + ۰٫۷
= ۱٫۴ ثانیه؛ همان عددی که Lighthouse گزارش کرد.

نکتهٔ مهم: این نقص روی **هر دو** صفحهٔ اصلی وجود داشت (`fa.html` و `en.html`)؛ فقط `/en`
به‌خاطر تفاوت اندازه/متن از آستانه رد شد. یعنی اگر فقط `/en` را «تعدیل» می‌کردیم، نقص
سر جایش می‌ماند.

## ۲. تصمیم

1. **انیمیشن ورودی hero با CSS اجرا می‌شود، نه با JS.** کلاس‌های `hero-enter` و
   `hero-enter--{rise,fade-up,fade,scale}` در `globals.css` تعریف شده‌اند. CSS هم‌زمان با
   parse شدن سند اجرا می‌شود، پس کندی شبکهٔ JS هرگز محتوا را پنهان نمی‌کند.
2. **عنصر کاندید LCP هیچ‌گاه از `opacity: 0` شروع نمی‌کند.** عنوان اصلی فقط
   `transform: translateY(20px) → 0` می‌گیرد؛ پس در نخستین رنگ‌آمیزی کاملاً دیده می‌شود و
   LCP به FCP گره می‌خورد. عناصر کوچک‌تر (eyebrow، زیرعنوان، CTA، کنواس، نشانگر اسکرول)
   می‌توانند fade داشته باشند، چون کاندید LCP نیستند.
3. **`prefers-reduced-motion: reduce`** همهٔ این انیمیشن‌ها را خاموش می‌کند (`animation: none`).
4. **نگهبان در سطح خروجی بیلد:** `npm run verify:rendering` علاوه بر بررسی pre-render،
   **هر ۵۶ فایل HTML پخته‌شده** را می‌خواند و اگر `<h1>` با `opacity: 0`،
   `visibility: hidden` یا `display: none` پیدا کند، بیلد و استقرار را متوقف می‌کند.
   برای ۱۴ مسیر عمومی، وجود `<h1>` هم اجباری است.

## ۳. پیامدها

**مثبت**

- LCP صفحهٔ اصلی از «وابسته به hydration» جدا شد؛ با حذف انیمیشن JS، LCP ≈ FCP.
- محتوای اصلی برای خزنده‌ها و کلاینت‌های بدون JS هم دیده می‌شود (پیش‌تر در HTML بود ولی
  نامرئی).
- `motion` از chunk ورودی hero حذف شد (۳۸٫۴ KB gz کمتر روی مسیر بحرانی صفحهٔ اصلی).
- رگرسیون دیگر بی‌صدا نیست: هم تست واحد (`hero.test.tsx`) و هم دروازهٔ خروجی بیلد.

**منفی / هزینه**

- انیمیشن‌های hero دیگر از API `motion` استفاده نمی‌کنند؛ برای تغییر تایمینگ باید
  `--hero-duration`/`--hero-delay` را در JSX یا کلاس‌های CSS عوض کرد. این هزینهٔ آگاهانه است:
  تایمینگ انیمیشن، چیزی نیست که به قیمت LCP تمام شود.
- سایر بخش‌های صفحه (پایین‌تر از fold) هنوز از `motion` استفاده می‌کنند؛ آن‌ها کاندید LCP
  نیستند و فعلاً دست‌نخورده‌اند. اگر روزی یکی از آن‌ها به بالای صفحه منتقل شد، دروازهٔ
  `verify:rendering` (برای `h1`) و بازبینی دستی (برای سایر عناصر بزرگ) لازم است.

## ۴. گزینه‌های بررسی‌شده و رد‌شده

| گزینه | چرا رد شد |
|---|---|
| تعدیل بودجهٔ Performance برای `/en` به ۰٫۹۰ | نقص در کد بود، نه در بودجه. تعدیل آستانه یعنی پذیرفتن «محتوا بعد از hydration ظاهر شود» — همان چیزی که ADR-0041 کل پروژه را برای رفعش بازنویسی کرد |
| نگه‌داشتن `motion` و حذف فقط `opacity` (فقط `y`) | همچنان تا hydration نامرئی‌بودنِ transform اعمال می‌شود؟ خیر، اما تایمینگ همچنان به JS گره می‌خورد؛ اندازه‌گیری نشان داد خودِ انتظار hydration بخش عمدهٔ تأخیر است |
| حذف کامل انیمیشن ورودی | طراحی از دست می‌رفت؛ CSS همان حس را با هزینهٔ صفر LCP می‌دهد |
| `ssr: false` برای کل hero | بدترین گزینه: HTML صفحه بدون محتوای اصلی می‌شد (سئو + FCP + LCP) |
| preload فونت انگلیسی به‌جای رفع انیمیشن | فرضیهٔ اولیه بود، ولی شواهد (FCP ۰٫۶ vs LCP ۱٫۴ و استایل inline در HTML) نشان داد مقصر فونت نیست؛ تغییر بی‌دلیل در مسیر فونت انجام نشد |

## ۵. قواعد اجرایی (برای آیندهٔ این ریپو)

1. هیچ عنصر بالای fold با `initial={{ opacity: 0 }}` (یا هر استایل inline معادل) رندر نشود.
2. انیمیشن ورودی محتوای اصلی، CSS-first باشد.
3. `npm run verify:rendering` پس از هر `npm run build` اجرا شود؛ در CI (جاب
   `frontend-test-build`) و در `scripts/deploy_frontend.sh` گام ۵ این کار انجام می‌شود.
4. هر ادعای کارایی دربارهٔ LCP باید با annotationهای Lighthouse (که نام سنجه و مقدار را
   می‌نویسند) یا با شاهد خروجی بیلد پشتیبانی شود — نه با حس.
