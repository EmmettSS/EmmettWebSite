# ADR-0005: استراتژی ذخیره‌سازی و امنیت Media

**وضعیت:** پذیرفته‌شده

## زمینه

پروژه روی هاست اشتراکی cPanel مستقر می‌شود، بدون فرض دسترسی به S3/CDN یا Redis. فایل‌های آپلودی (تصاویر پروژه‌ها، عکس تیم، مدارک) باید به‌صورت امن ذخیره و سرو شوند، مطابق قانون ۱۶ (امنیت) و قانون ۱۵ (کارایی).

## گزینه‌ها

1. **ذخیرهٔ ابری (S3-compatible, مثل Arvan/Liara Object Storage):** مقیاس‌پذیرتر، CDN رایگان، ولی هزینهٔ اضافه + وابستگی به سرویس خارجی + پیچیدگی پیکربندی credential که فعلاً در دسترس/تأییدشده نیست.
2. **ذخیرهٔ لوکال روی دیسک هاست، سرو مستقیم توسط Apache:** بدون هزینهٔ اضافه، بدون وابستگی جدید، کاملاً سازگار با فرض محافظه‌کارانهٔ هاست؛ محدودیت مقیاس (ظرفیت دیسک هاست اشتراکی) پذیرفته می‌شود.

## تصمیم

**گزینهٔ ۲ (لوکال)** برای فاز اول؛ انتزاع ذخیره‌سازی Django (`DEFAULT_FILE_STORAGE` / `STORAGES`) طوری پیکربندی می‌شود که مهاجرت به object storage در آینده فقط یک تغییر تنظیمات باشد، نه بازنویسی کد.

## دلیل

- در `DISCOVERY.md` فرض محافظه‌کارانهٔ هاست (بدون سرویس جانبی) پذیرفته شده؛ افزودن یک سرویس ابری جدید بدون تأیید صریح هزینه/دسترسی، نقض قانون ۶ (بدون وابستگی غیرضروری) است.
- مدل مرکزی `core.Media` و استفادهٔ انحصاری `FileField`/`ImageField` از طریق Django Storage API باعث می‌شود تغییر backend ذخیره‌سازی در آینده (در صورت رشد ترافیک) بدون تغییر در مدل‌های دیگر ممکن باشد.

## جزئیات طراحی امنیتی

- مسیر آپلود: `media/{media_type}/%Y/%m/{uuid4}_{slug}.{ext}` — جلوگیری از افشای نام فایل اصلی و برخورد نام.
- Whitelist سخت‌گیرانهٔ پسوند و MIME (`image/jpeg, image/png, image/webp, image/svg+xml (sanitize شده), application/pdf, .docx`)؛ بررسی magic bytes فایل، نه فقط پسوند ارسالی کاربر.
- محدودیت حجم: تصویر ≤ ۵MB، سند ≤ ۱۰MB (قابل تنظیم در `.env`، نه hard-code).
- دایرکتوری `media/` با `.htaccess` اجرای اسکریپت را غیرفعال می‌کند (`php_flag engine off` + `Options -ExecCGI`) تا حتی در صورت عبور یک فایل مخرب از اعتبارسنجی، قابل اجرا نباشد.
- آپلودها فقط از طریق کاربران احراز‌هویت‌شده با نقش مجاز (staff/editor) ممکن است؛ آپلود مستقیم عمومی (بدون احراز هویت) وجود ندارد.
- اسکن ویروس با `clamd` در صورت در دسترس بودن روی هاست، به‌صورت best-effort و غیرمسدودکننده (اگر سرویس موجود نبود، سایت از کار نمی‌افتد).

## پیامدها

- ظرفیت دیسک هاست باید پایش شود (Audit دوره‌ای)؛ در صورت نزدیک‌شدن به سقف، تصمیم مهاجرت به Object Storage باید دوباره باز شود.
- بکاپ‌گیری از `media/` باید جزو برنامهٔ بکاپ هاست (فاز Deployment) باشد، جدا از بکاپ دیتابیس.

## به‌روزرسانی (فاز ۴ — اجرای واقعی اعتبارسنجی)

در فاز ۲ مدل `core.Media` ساخته شد اما whitelist پسوند/MIME، بررسی magic
bytes و محدودیت حجم عملاً پیاده‌سازی نشده بودند (شکاف کشف‌شده در
بازبینی/سخت‌سازی فاز ۴). اکنون `apps/core/validators.py` این سه لایه را
پیاده‌سازی می‌کند:

- `media_extension_validator` (`FileExtensionValidator` استاندارد Django)
  روی خودِ فیلد `Media.file`.
- `validate_media_file_size` در `Media.clean()` — سقف از `settings.MEDIA_MAX_IMAGE_SIZE_MB`/`MEDIA_MAX_DOCUMENT_SIZE_MB` (پیش‌فرض ۵/۱۰، از `.env` قابل تنظیم) خوانده می‌شود.
- `validate_media_file_signature` در `Media.clean()` — به‌جای افزودن
  وابستگی `python-magic` (که به `libmagic` سیستمی نیاز دارد و توجیه کافی
  برای نقض قانون ۶ نداشت)، یک جدول کوچک سرنام بایت اول فایل‌های مجاز
  (jpg/png/webp/pdf/docx) به‌صورت دستی بررسی می‌شود؛ svg (متن XML، بدون
  سرنام باینری ثابت) از این بررسی مستثناست و فقط sanitize آن (طبق بند
  whitelist بالا) هنوز در scope این پروژه پیاده‌سازی **نشده** و به فاز بعد
  موکول می‌شود.
- فایل `backend/deploy/media.htaccess.example` اضافه شد؛ باید در زمان
  دیپلوی production به `backend/media/.htaccess` کپی شود (خودِ `media/` در
  `.gitignore` است، پس نمی‌تواند مستقیماً commit شود).
- اسکن ویروس با `clamd` همچنان پیاده‌سازی **نشده** (به فاز Deployment/Infra
  موکول شد؛ وابسته به در دسترس‌بودن سرویس روی هاست production).
- آپلود فقط از طریق Django Admin ممکن است (هیچ endpoint عمومی آپلود در
  API وجود ندارد)، پس اعتبارسنجی فقط برای کاربران staff/editor اعمال
  می‌شود، دقیقاً طبق تصمیم اصلی این ADR.
