# ADR-0004: استراتژی تاریخ شمسی/میلادی و اعداد فارسی/لاتین

**وضعیت:** پذیرفته‌شده

## زمینه

قانون ۱۰: «تاریخ‌ها: در فارسی شمسی (jdatetime)، در انگلیسی میلادی. اعداد: فارسی در FA، لاتین در EN.» این باید هم در بک‌اند (ادمین، اعلان‌های پیامکی/ایمیلی) و هم در فرانت (صفحات عمومی سایت) رعایت شود، بدون اینکه لایهٔ دادهٔ API قابل کش و بدون‌حالت بودنش را از دست بدهد.

## گزینه‌ها

1. **ذخیرهٔ تاریخ شمسی در دیتابیس:** ساده‌ترین برای نمایش فارسی، ولی تمام محاسبات/مرتب‌سازی/فیلتر تاریخ را پیچیده و غیراستاندارد می‌کند؛ پشتیبانی ORM/ایندکس را دشوار می‌کند؛ خلاف best-practice.
2. **ذخیرهٔ میلادی استاندارد + تبدیل در لحظهٔ serialize (بک‌اند)، ارسال رشتهٔ از پیش فرمت‌شده به فرانت:** API به ازای هر locale پاسخ متفاوت می‌دهد → کش‌پذیری API کاهش می‌یابد (باید per-locale cache کرد).
3. **ذخیرهٔ میلادی استاندارد (UTC) + API همیشه ISO-8601 خام برمی‌گرداند + فرمت‌دهی نهایی (شمسی/میلادی، فارسی/لاتین) در لایهٔ نمایش (فرانت Next.js) انجام می‌شود؛ بک‌اند فقط در سطوح خودش (Django Admin، قالب پیامک/ایمیل) مستقیماً از `jdatetime` استفاده می‌کند.**

## تصمیم

**گزینهٔ ۳.**

## دلیل

- جدا نگه‌داشتن ذخیره‌سازی (همیشه میلادی/UTC) از نمایش، استاندارد صنعتی است و با ORM/ایندکس‌گذاری (قانون ۱۵) کاملاً سازگار می‌ماند.
- API که همیشه ISO-8601 خام برمی‌گرداند، **locale-agnostic و کاملاً کش‌پذیر** است (یک نسخه از پاسخ برای همه، صرف‌نظر از زبان کاربر) — سازگار با `ADR-0006`.
- Django Admin (که توسط کارکنان فارسی‌زبان استفاده می‌شود) و قالب‌های اعلان پیامکی/ایمیلی (که مستقیماً توسط بک‌اند رندر می‌شوند) باید خوانا و شمسی باشند؛ این دو مورد مستقیماً در بک‌اند با `jdatetime` از طریق یک util مشترک (`core.utils.dates.to_jalali_display`) فرمت می‌شوند — اینجاست که `jdatetime` طبق قانون ۱۰ واقعاً استفاده می‌شود.
- تبدیل برای کاربر نهایی سایت (در Next.js) با یک کتابخانهٔ سبک JS (مثل `dayjs` + پلاگین تقویم جلالی) انجام می‌شود که با همان قرارداد (ISO ورودی → نمایش شمسی/میلادی + اعداد فارسی/لاتین خروجی) کار می‌کند؛ این انتخاب کتابخانهٔ فرانت در فاز Implementation فرانت با توجیه dependency بررسی می‌شود (قانون ۶).
- تبدیل اعداد (فارسی⇄لاتین) به همین ترتیب در لایهٔ نمایش انجام می‌شود: `core.utils.numerals.to_fa_digits()` برای بک‌اند (ادمین/پیامک) و معادل آن در فرانت.

## پیامدها

- باید یک util مرکزی مستند در `apps/core/utils/dates.py` و `numerals.py` ساخته شود؛ استفادهٔ مستقیم و پراکنده از `jdatetime`/تبدیل رشته در کدهای مختلف ممنوع است (DRY + قابلیت تست).
- تست واحد برای این دو util الزامی است (مرز تاریخ‌های کبیسهٔ شمسی، انتقال سال نو، صفر/منفی بودن عدد).
- وابستگی جدید بک‌اند: `jdatetime` (توجیه: کوچک، بدون وابستگی ترانزیتیو سنگین، دقیقاً پاسخ‌گوی الزام صریح قانون ۱۰).
