# ADR-0022: Markdown به‌عنوان فرمت یکدست تمام محتوای طولانی

**وضعیت:** پذیرفته‌شده

## زمینه

`ARCHITECTURE.md` (فاز ۱) فیلدهای توضیح طولانی (`Service.description`, `Project`/`CaseStudy` بخش‌های مختلف، `Course.description`, `Lesson.content`) را «richtext» نام‌گذاری کرده بود، بدون قطعی‌کردن HTML در برابر Markdown. بریف فاز ۴ برای بلاگ صراحتاً Markdown خواسته. این ابهام (آیا بقیهٔ محتوای طولانی هم Markdown باشد یا HTML richtext جدا) از مالک محصول پرسیده شد؛ پاسخ: Markdown برای همه‌جا.

## گزینه‌ها

1. **Markdown همه‌جا:** یک فرمت ذخیره‌سازی یکدست برای تمام فیلدهای محتوای طولانی؛ ادیتور ادمین ساده (textarea + پیش‌نمایش)، بدون نیاز به کتابخانهٔ WYSIWYG سنگین.
2. **Markdown فقط برای بلاگ، HTML richtext (`django-ckeditor`/TipTap) برای بقیه:** نزدیک‌تر به توصیف اولیهٔ `ARCHITECTURE.md`، اما یک وابستگی سنگین اضافه (ادیتور JS کامل + ذخیرهٔ HTML خام که نیاز شدیدتری به sanitize دارد) فقط برای چند مدل.

## تصمیم

گزینهٔ ۱. هر فیلد محتوای طولانی (`description`, `content`, بخش‌های `CaseStudy`) به‌صورت Markdown خام در دیتابیس ذخیره می‌شود. پیاده‌سازی:

- `apps/core/utils/markdown.py`: تابع `render_markdown(raw_markdown: str) -> str` که با کتابخانهٔ `Markdown` (extensions: `extra`, `toc`, `tables`, `fenced_code`) Markdown را به HTML تبدیل می‌کند، سپس خروجی را با `nh3` (sanitizer مبتنی بر Rust/ammonia؛ جایگزین `bleach` که دیگر نگه‌داری نمی‌شود) با یک allowlist محدود از تگ/属性 پاک‌سازی می‌کند — جلوگیری از XSS حتی اگر محتوا توسط نویسندهٔ داخلی (نه الزاماً کاملاً مطمئن) وارد شده باشد (قانون ۱۶).
- تابع کمکی `extract_toc(html: str) -> list[dict]` فهرست هدینگ‌های `h2`/`h3` (تولیدشده توسط افزونهٔ `toc`، که از پیش `id` به هر هدینگ اضافه می‌کند) را برای ساخت «فهرست مطالب» (TOC) بلاگ استخراج می‌کند.
- تابع `estimate_reading_time(raw_markdown: str, words_per_minute: int = 200) -> int` برای محاسبهٔ خودکار `BlogPost.reading_time_minutes`.
- رندر HTML در زمان `save()` مدل محاسبه و در یک فیلد مجزای غیرقابل‌ویرایش (`*_html`, مثلاً `content_html`) کش می‌شود تا هر درخواست API مجبور به رندر دوبارهٔ Markdown نباشد (کارایی — قانون ۱۵)؛ منبع حقیقت (source of truth) همیشه فیلد Markdown خام است.
- در API، هر فیلد محتوای Markdown هم مقدار خام (`content_md`) و هم HTML رندرشده (`content_html`) را برمی‌گرداند — فرانت‌اند بسته به نیاز (ویرایش در آینده در برابر نمایش) یکی را مصرف می‌کند.

## دلیل

- یکدست‌بودن فرمت در تمام اپ‌ها، نگه‌داری/بازبینی کد ساده‌تر می‌کند (یک تابع render/sanitize مشترک، نه چند ادیتور/فرمت مختلف).
- Markdown خام در دیتابیس، دیف‌پذیر و قابل‌بازبینی (code-review-friendly) است؛ بدون نیاز به یک کتابخانهٔ JS سنگین WYSIWYG در ادمین Django.
- محاسبهٔ `reading_time`/TOC به‌طور طبیعی از همان تابع رندر Markdown مشتق می‌شود، بدون منطق تکراری.
- `nh3` روی `bleach` ترجیح داده شد چون `bleach` به‌طور رسمی اعلام نگه‌داری نشدن کرده (ریسک امنیتی بلندمدت یک وابستگی رها شده)، درحالی‌که `nh3` (بایندینگ پایتونی کتابخانهٔ فعال `ammonia` به زبان Rust) نگه‌داری فعال دارد.

## پیامدها

- اگر در آینده نیاز به ادیتور WYSIWYG واقعی در ادمین پیدا شد (نه فقط textarea Markdown)، باید یک ADR جدید برای افزودن یک ادیتور Markdown-aware (نه HTML richtext) نوشته شود تا فرمت ذخیره‌سازی یکدست نشکند.
- هر فیلد Markdown جدید در مدل‌های آینده باید دقیقاً از همین الگو (فیلد خام + فیلد `_html` کش‌شده + رندر در `save()`) پیروی کند.
- محتوای کاربر نهایی (مثل `Comment.body`) **Markdown نیست** — متن ساده با escape خودکار HTML است؛ این تصمیم محدود به محتوای نویسندگان/ادمین است، نه ورودی عمومی کاربران (کاهش سطح حملهٔ XSS).
